# AWS CI/CD Demo

A simple AWS CI/CD demonstration using **GitHub Actions, GitHub OIDC, AWS IAM, Amazon S3, AWS Systems Manager (SSM), EC2, and an Application Load Balancer (ALB)**.

The project uses Terraform to provision the AWS infrastructure and generate the GitHub Actions deployment workflow.

## Architecture

```text
GitHub Application Repository
        |
        | GitHub Actions
        | OIDC authentication
        v
AWS IAM Role
        |
        +--------------------+
        |                    |
        v                    v
   S3 Bucket             AWS SSM
   Deployment            SendCommand
   Artifact                  |
        |                    v
        +--------------->  EC2
                            |
                         Apache
                            |
                            v
                           ALB
                            |
                            v
                         Internet
```

The deployment flow is:

1. A change is pushed to the application's `main` branch.
2. GitHub Actions authenticates to AWS using GitHub OIDC.
3. GitHub Actions creates a ZIP deployment artifact.
4. The artifact is uploaded to a private S3 bucket.
5. GitHub Actions uses AWS Systems Manager to send a deployment command to the EC2 instance.
6. EC2 downloads the artifact from S3 and updates the web page.
7. The application is served through the Application Load Balancer.

# Prerequisites

Before starting, make sure you have:

* An AWS account
* An AWS IAM identity that can create the required resources
* Terraform `>= 1.15.0`
* Git
* A GitHub account
* An AWS region to use
* An existing VPC
* A subnet for the EC2 instance
* Two subnets in different Availability Zones for the Application Load Balancer

You should also have AWS authentication configured locally so that Terraform can authenticate to AWS.

Do **not** store AWS access keys, passwords, or other secrets in this repository.

# 1. Create the Application GitHub Repository

First, create a **new blank GitHub repository** for the application.

For example:

```text
aws-cicd-demo-app
```

The repository can be private or public.

At this stage, the application repository should be blank.

You will add the application files generated by Terraform later.

> Important: The GitHub repository must exist before you configure the `github_subject` variable because the GitHub OIDC subject is based on the application repository.

# 2. Clone This Infrastructure Repository

```bash
git clone <YOUR_INFRASTRUCTURE_REPOSITORY_URL>
cd <YOUR_INFRASTRUCTURE_REPOSITORY_DIRECTORY>
```

# 3. Create the Terraform Backend Configuration

This project uses an S3 backend for Terraform state.

The backend S3 bucket must exist before Terraform initializes the backend.

Create a file named:

```text
backend.hcl
```

Use the provided example as a starting point:

```text
backend.hcl.example
```

Example:

```hcl
bucket = "YOUR-TERRAFORM-STATE-BUCKET"
key    = "YOUR-PROJECT/terraform.tfstate"
region = "us-east-1"
```

Replace the placeholder values with your Terraform state bucket and desired state path.

`backend.hcl` is intentionally ignored by Git and should not be committed.

Initialize Terraform:

```bash
terraform init -backend-config=backend.hcl
```

---

# 4. Create Your Terraform Variables File

Copy the example file:

```text
terraform.tfvars.example
```

to:

```text
terraform.tfvars
```

For example, on Windows:

```bash
copy terraform.tfvars.example terraform.tfvars
```

On Linux/macOS:

```bash
cp terraform.tfvars.example terraform.tfvars
```

Then provide your actual AWS values.

Example:

```hcl
aws_region             = "us-east-1"
ami_id                 = "YOUR_AMI_ID"
instance_type          = "t3.micro"
subnet_id              = "YOUR_EC2_SUBNET_ID"
vpc_id                 = "YOUR_VPC_ID"

deployment_bucket_name = "YOUR-UNIQUE-DEPLOYMENT-BUCKET-NAME"

github_subject         = "repo:YOUR_ORG/YOUR_REPO:ref:refs/heads/main"

alb_subnet_1_id        = "YOUR_FIRST_ALB_SUBNET_ID"
alb_subnet_2_id        = "YOUR_SECOND_ALB_SUBNET_ID"
```

### Important

`terraform.tfvars` is ignored by `.gitignore`.

**Do not commit it to GitHub.**

The repository contains `terraform.tfvars.example` so that users know which variables are required without exposing their actual configuration.

# 5. Get the GitHub OIDC Subject

The `github_subject` value restricts which GitHub repository and branch can assume the AWS IAM role.

Go to your **application repository**:

```text
GitHub
→ Application Repository
→ Settings
→ Actions
→ OIDC
```

Look inside the:

```text
Default subject claim prefix
```

box.

Copy the subject information shown there.

Use your repository's actual subject in `terraform.tfvars`.

The expected format is:

```text
repo:YOUR_ORG/YOUR_REPO:ref:refs/heads/main
```

For example:

```hcl
github_subject = "repo:YOUR_ORG/YOUR_REPO:ref:refs/heads/main"
```

Replace:

```text
YOUR_ORG/YOUR_REPO
```

with your actual GitHub organization/user and application repository.

Keep:

```text
:ref:refs/heads/main
```

at the end.

This means the GitHub Actions role is restricted to the specified repository's `main` branch.

# 7. Create the AWS Infrastructure

Once the plan looks correct:

```bash
terraform apply
```

Review the resources Terraform is going to create.

Enter:

```text
yes
```

when prompted.

Terraform will create the infrastructure required for the deployment, including:

* EC2 instance
* IAM role and instance profile for EC2
* AWS Systems Manager permissions
* S3 deployment bucket
* S3 security settings
* GitHub OIDC provider
* GitHub Actions IAM role
* GitHub Actions S3 permissions
* GitHub Actions SSM permissions
* Application Load Balancer
* Target group
* ALB listener
* Security groups

### Application URL

After `terraform apply` completes, Terraform will display an output similar to:

```text
alb_dns_name = "http://aws-cicd-demo-alb-123456789.us-east-1.elb.amazonaws.com"
```

This is the URL of the Application Load Balancer.

Open the displayed URL in your browser to access the application.

You can also retrieve the URL at any time with:

```bash
terraform output -raw alb_dns_name
```

> The ALB currently uses HTTP, so the URL starts with `http://`.

# 12. GitHub Actions Deployment

Pushing the application to `main` triggers:

```text
.github/workflows/deploy.yaml
```

The workflow:

1. Checks out the application repository.
2. Authenticates to AWS using GitHub OIDC.
3. Assumes the Terraform-created IAM role.
4. Creates a ZIP deployment artifact.
5. Uploads the artifact to the private S3 deployment bucket.
6. Sends an SSM command to the EC2 instance.
7. EC2 downloads the artifact from S3.
8. The application file is copied to Apache's web directory.
9. Apache is restarted.
10. The workflow waits for the SSM command to complete.

No SSH connection is required for deployment.

# Security Considerations

This project intentionally uses several AWS and GitHub security features.

### GitHub OIDC

GitHub Actions authenticates to AWS using OIDC instead of storing long-lived AWS access keys in GitHub.

The IAM trust policy restricts which GitHub repository and branch can assume the role.

### S3

The deployment bucket is configured with:

* Block Public Access enabled
* Bucket owner enforced
* Server-side encryption
* Versioning enabled

Deployment artifacts are stored under:

```text
deployments/
```

### IAM

The EC2 instance uses an IAM instance profile rather than AWS credentials stored on the server.

The EC2 role has SSM permissions and access to download deployment artifacts from the deployment bucket.

The GitHub Actions role has permissions required for:

* Uploading deployment artifacts to S3
* Sending deployment commands through SSM
* Reading SSM command results

### EC2

The EC2 security group allows HTTP traffic from the ALB security group rather than allowing HTTP traffic directly from the internet.

The application is accessed through the Application Load Balancer.

### Secrets

Do not commit:

```text
terraform.tfvars
*.tfstate
*.tfstate.*
backend.hcl
AWS access keys
SSH private keys
passwords
API tokens
other secrets
```

The included `.gitignore` is configured to exclude the Terraform state, variable files, backend configuration, and generated application directory.

# Important: Terraform State

Terraform state can contain sensitive infrastructure information.

Do not commit:

```text
terraform.tfstate
terraform.tfstate.*
```

This project uses an S3 backend so that Terraform state can be stored outside the Git repository.

Make sure the Terraform state bucket itself is appropriately secured.

# Updating the Application

To deploy a new application version:

1. Modify `index.html` in the application repository.
2. Commit the change.
3. Push to `main`.
4. GitHub Actions automatically runs the deployment workflow.
5. The updated file is uploaded to S3.
6. SSM deploys the new version to EC2.

Example:

```bash
git add .
git commit -m "Update application"
git push origin main
```

---

# Updating the Infrastructure

Infrastructure changes should be made in this Terraform repository.

After making changes:

```bash
terraform fmt
terraform validate
terraform plan
terraform apply
```

If Terraform changes values used by the generated GitHub Actions workflow, regenerate the application files and copy the updated files into the application repository.

---

# Cleanup

When the demo is no longer needed, destroy the Terraform-managed infrastructure:

```bash
terraform destroy
```

Review the resources Terraform plans to remove before confirming.

Also check the AWS console afterward to make sure any resources that were created outside Terraform, such as the Terraform state bucket, are handled separately if they are no longer needed.
